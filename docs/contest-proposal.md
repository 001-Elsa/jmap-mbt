## 选题动机与生态价值

邮件列表的顺序变化与对象属性变化来自两条独立的 JMAP 历史。查询顺序没变，不意味着邮件未读状态、摘要等属性没变；删除有界列表中的一个成员，也不能直接把剩余短列表判为完整。如果调用方混用不同 queryState 的补位页，或把迟到响应覆盖新视图，界面可能展示一个无法由同一状态解释的前缀。

MoonJMAP 为 MoonBit 调用方提供一个不持有网络连接的同步内核：输入已取得的四种固定 JMAP 响应，输出下一个明确请求、可恢复待办，或满足契约的有序前缀。适用对象是准备在 MoonBit 中维护只读邮件查询列表的开发者，不宣称已经有生产用户或所有服务均可兼容。

## 生态近邻与另建项目的理由

`moonreconcile`、`MoonCDC`、`incr`、`moon_taskforge`、`moonreplaykit`、`moontxnwitness`、`medseal`、`moon_historycheck` 等与本项目共享集合差异、状态恢复、前缀门禁或独立义务重算等机制，HTTP/JSON 和邮件协议包也已存在。并非生态中没有相关技术。

当前另建的理由是交付边界集中于 JMAP 的 `Email/changes` 与 `Email/queryChanges` 两条 state、同 queryState 补位、ID 归位和邮件查询领域证书。将这些语义塞进通用 CDC 或集合工具会把 JMAP 账户、查询身份和四方法契约带入原项目；作为独立小库更便于限定协议边界，通用传输仍由已有生态或调用方承担。这是架构取舍说明，不是已经与上述维护者协商合作的声明。

指定目录与源码快照的相似性记录见 README 及 `outputs/` 报告；没有完整官方参赛名单，不能证明与所有参赛项目无重合。章程第4.1条的最终认定归主办方。

## 交付范围与明确边界

已实现：两种固定查询视图、四方法有限 typed 模型、双 state 追赶、按最终排名归并、同状态补位、对象完整性门禁、累计变化预算、generation 拒绝旧响应、checkpoint 恢复、位置证书生成与离线验证。代码集中于 `src/email`、`src/jmap` 和 `src/sync`。

不在范围内：HTTP/TLS/OAuth、Session/SSE、完整邮件客户端、SMTP/IMAP/MIME、正文附件、发送写入、任意查询构造器和通用 RPC/日志/工作流引擎。Python wire 与调查工具是支撑材料。来源与真实服务验证的限制见 [来源清单](source-provenance.md) 和 README。

## 技术路径与可复现交付

先把账号、查询身份、两个 opaque token 和代次绑定到请求票据，再校验固定响应。列表增量按服务端最终排名产生连续已知前缀；出现缺口时在同一 queryState 补位。对象链单独追赶，预算不足保持 Pending，历史失效进入重建。只有两链无待办、对象覆盖完整、前缀完整时才允许 Ready。位置证书保存旧位置引用或新增 ID，验证器重算结构化边界；它不能单凭证书证明真实邮件字段的来源。

可复现入口：`moon run cmd/demo --target wasm`；三个后端的检查、构建、测试由 `.github/workflows/ci.yml` 执行。测试包含边界回归、最终排名枚举、证书转移、独立 Python oracle 和 C01–C15 有界跨实现对拍。真实服务记录只覆盖此前本机 Stalwart v0.16.27 的固定只读路径；本次改动不扩展该结论。
