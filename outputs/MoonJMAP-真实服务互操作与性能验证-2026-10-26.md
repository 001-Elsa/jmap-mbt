# MoonJMAP 真实 JMAP 服务互操作与性能验证（2026-10-26）

## 结论

本次完成了两类针对**真实 JMAP 服务实现**的证据：一份空邮箱上的协议探针记录，以及一份在同一真实服务中预置 5 封合成邮件后的对象级性能运行。测试对象是从 Stalwart 官方发布物取得的 **Stalwart Server v0.16.27**（aarch64 macOS），使用临时 RocksDB 数据目录启动；测试账号和密码只存在于运行进程环境，没有写入仓库、报告或证据文件。服务停止后，临时运行目录不作为交付物。

在修正 RFC 8620 的 `Email/queryChanges` 可选 `total` 字段后，以下四个 JMAP Mail 方法均由真实 Stalwart 服务返回 HTTP 200，并被 live JMAP envelope/parser 接受。空邮箱探针还通过 MoonJMAP 的 typed wire decoder 验证了相同方法的 wire 形状；对象级运行的 `Email/query` 每次返回 5 个 ID，`Email/get` 每次返回 5 个真实对象，5 轮累计解析 25 个对象且 `notFound=0`。非空运行的原始响应体按脱敏策略未保存，因此不把非空对象重新通过 typed decoder 的动作写成已发生：

1. `Email/query`
2. `Email/get`
3. `Email/changes`
4. `Email/queryChanges`

Session 也返回了 JMAP Core 和 JMAP Mail capability。空邮箱互操作记录是脱敏 JSON，只保留方法、HTTP 状态、计数、固定属性名、稳定哈希和响应摘要：

## 这次修正的协议问题

第一次真实探针运行时，Stalwart 的无变化 `Email/queryChanges` 响应省略 `total`，探针将其标记为 `ProtocolFailure`。查阅 RFC 8620 §5.6 后确认：`total` 只在请求带 `calculateTotal: true` 时返回，省略是符合标准的行为。于是将 `EmailQueryChangesResponse.total` 改为可选字段：带字段时继续做非负值和 added index 检查，缺省时保留 `None` 并在重新编码时省略该字段。新增回归测试覆盖该标准场景。

这不是放宽服务器专属规则，而是修复 MoonJMAP wire model 对 RFC 的错误必填假设。原始失败记录仍保留，便于复核这次真实互操作发现：

- [record-empty.json](real-interop-stalwart-v0.16.27/record-empty.json)

## 范围与限制

这次结果证明 MoonJMAP 的只读适配层能够和 Stalwart v0.16.27 的真实实现完成上述固定方法序列，并在非空邮箱中解码真实 Email 对象；它不证明所有 JMAP 服务、所有过滤器、所有分页规模、TLS/OAuth 部署或 JMAP 写操作都兼容。`Email/changes` 和 `Email/queryChanges` 本次返回的是有效的无变化分支，没有把创建、更新或删除事件伪造成已覆盖。性能数据是本机 loopback、临时服务、5 封合成邮件下的工程基准，不应解释成公网延迟、吞吐、容量或生产 SLO。

本次没有可合法使用的第三方托管邮箱 token，因此没有把 Fastmail 的无凭据 HTTP 401 写成互操作结果。该外部端点可达记录仍保留在 `outputs/real-benchmark/fastmail-unauthenticated-2026-10-26.json`，其 `performance_claim=false`。
