# MoonJMAP 真实对象级 JMAP 互操作证据（2026-10-26）

## 结论

本文件把一次已经完成的真实服务性能运行转换成对象级互操作证据，解决“探针调用了 `Email/get`，但空邮箱记录看不出真实对象”的可审计问题。运行对象是官方发布的 **Stalwart Server v0.16.27**，在本机 loopback HTTP 端口运行；邮件数据是专门为测试注入的合成数据，账号、邮箱、邮件 ID、state、正文、主题和地址没有写入证据。

在这次 live HTTP 运行中，MoonJMAP 的请求真正到达 Stalwart，且所有 20 个 HTTP 请求均返回 2xx：

- `Email/query` 5 次，每次返回 5 个邮件 ID，`total=5`；
- `Email/get` 5 次，每次返回 5 个邮件对象，累计解码 25 个对象，`notFound=0`；
- `Email/changes` 5 次，每次返回有效的无变化响应；
- `Email/queryChanges` 4 次，每次返回有效的无变化响应；
- JMAP Session 返回 Core、Mail 及相关 capability，Session HTTP 状态为 200。

对象级脱敏记录见：

- [record-seeded-object-level-20261026.json](real-interop-stalwart-v0.16.27/record-seeded-object-level-20261026.json)

该记录由以下真实运行的脱敏性能证据确定性派生，保留了每个 HTTP 事件的状态、耗时、请求/响应字节数、wire 哈希及 typed response summary：

- [stalwart-local-real-20261026-seeded.json](real-benchmark/stalwart-local-real-20261026-seeded.json)

派生工具为 [derive_real_interop_record.py](../scripts/derive_real_interop_record.py)。它只读取已完成的脱敏运行记录，不重放请求，也不生成响应。

## 真实 HTTP 证据

| 方法 | 调用次数 | 每次观察到的结果 | 解码结论 |
| --- | ---: | --- | --- |
| Session `GET` | 1 | HTTP 200；返回 JMAP Mail capability | Session URL、API URL、账号选择和 capability 解码成功 |
| `Email/query` | 5 | HTTP 200；`ids_count=5`、`total=5` | 查询状态和 5 个 ID 列表解码成功 |
| `Email/get` | 5 | HTTP 200；`objects_count=5`、`not_found_count=0` | 25 个真实 Email 对象被解码；属性包括 `id`、`threadId`、`mailboxIds`、`keywords`、`receivedAt`、`subject`、`from`、`preview` |
| `Email/changes` | 5 | HTTP 200；created/updated/destroyed 均为 0 | `oldState`、`newState` 和无变化列表解码成功 |
| `Email/queryChanges` | 4 | HTTP 200；added/removed 均为 0，`total` 省略 | `oldQueryState`、`newQueryState` 和增量列表解码成功；省略 `total` 符合 RFC 8620 的可选语义 |

该运行的 20 个请求中没有失败项。对象 ID、账号 ID、邮箱 ID 和 state 只以稳定哈希保留，不能从记录反推出原始值；这也是记录可以放入项目交付物而不暴露测试凭据或邮件内容的原因。

需要区分两层证据：这份非空记录是从真实性能工具的 live HTTP observations 派生的；性能工具对 JMAP 三元组、方法名、状态字段、对象列表和计数做了严格解析。较早的空邮箱记录则是通过 `JmapHttpProbe` 的 `src/jmap` typed wire decoder 生成的。由于原始非空响应体按脱敏策略没有保存，本文件不把非空对象重新喂给 typed decoder 的动作写成已经发生；它证明的是同一固定请求序列在真实服务上返回了非空对象和可解析的响应形状。

## 运行和性能上下文

- 服务：Stalwart Server v0.16.27 官方二进制；`deployment=local-real-stalwart`。
- 网络：`127.0.0.1:8080` loopback HTTP；性能工具显式允许本地明文 HTTP。
- 认证：Basic；记录只保留 `credential_present=true`，不保留用户名、密码或 Authorization 头。
- 数据：5 封测试用合成邮件；运行前已写入本地测试邮箱，运行本身只进行 JMAP 读和增量查询。
- 参数：5 轮、`prefix_limit=20`、`maxObjectsInGet=50`、20 秒请求超时。
- 真实测量：请求 4,644 字节，响应 15,021 字节；RTT 最小/平均/P50/P95/最大为 4.771/8.627/6.985/13.467/26.708 ms。
- 运行状态：`status=complete`、`performance_claim=true`、20/20 HTTP 2xx。

这些数值是这次本机运行的可复核工程测量，不是公网延迟、吞吐、容量或生产 SLO。原始响应体没有保存，保留的是响应摘要和 SHA-256 wire 哈希。

## 与空邮箱探针记录的关系

较早的只读探针记录仍然有效，但它使用空 Inbox，四个 Mail 方法都返回空列表，因此只能证明空数据集上的 wire 互操作：

- [record-empty.json](real-interop-stalwart-v0.16.27/record-empty.json)
- [record-complete-20261026.json](real-interop-stalwart-v0.16.27/record-complete-20261026.json)

本文件及 `record-seeded-object-level-20261026.json` 才是非空 Email 对象证据。为了避免误读，`record-complete-20261026.json` 的元数据仍明确标为 `probe=read-only`，不能把它当作非空对象记录。

## 证据边界

这次已经证明真实 Stalwart 实现对固定的 Session、查询、对象获取和两类增量读取请求能返回可被 live JMAP envelope/parser 接受的响应，并且 `Email/get` 确实返回了非空对象；空邮箱探针还单独证明了相同四种方法可以通过 MoonJMAP typed wire decoder。由于非空原始响应没有留存，不能把二者合并写成“非空对象已重新通过 typed decoder”。`Email/changes` 和 `Email/queryChanges` 在本次运行中是无变化分支；记录没有制造删除、移动、更新或创建事件来冒充增量覆盖。

这次运行没有证明：

- 通过 JMAP `Email/set`/`Email/import` 写入邮件的互操作；
- 非空 `Email/changes` 或 `Email/queryChanges`（创建、更新、删除、移动）变化链；
- 第三方托管服务、生产 TLS/OAuth、所有过滤器和任意数据规模的兼容性；
- 公网性能或生产级容量。

因此，交付物可以准确声称“在真实 Stalwart v0.16.27 上完成了带真实 Email 对象的 HTTP 互操作和本机性能测量”，不能扩大为所有 JMAP 服务或所有写/变化场景均已通过。
