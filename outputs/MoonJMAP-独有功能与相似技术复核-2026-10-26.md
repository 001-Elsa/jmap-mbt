## 结论

**在本次 Mooncakes 当前公开发布版本、静态源码遍历和候选实现复核范围内，尚未发现可直接替代 MoonJMAP“JMAP 邮件有序查询前缀的双状态同步及其前缀转移见证”这一完整工作流的模块。但没有依据确认任何单项技术与其他所有项目完全不重合、不类似。**

两个判断应同时保留：

1. **功能组合有区分度。** 对象状态 `Email state` 与查询顺序状态 `queryState` 分链；协调 `Email/changes`、`Email/queryChanges`、`Email/query`、`Email/get`；只维护从位置 0 开始的有界有序前缀；缺口按相同 queryState 补位；输出下一请求、恢复状态及领域转移见证。
2. **组成技术已有明确邻居。** 增量投影、有限窗口、连续确认前缀、缺口保护、scope/epoch 隔离、generation、checkpoint、预算、remove/add、规划器、witness、离线重放、前缀一致性验证和 FNV 指纹都能在其他发布源码中找到类似机制。

因此，可以说“本次快照未发现同目的完整实现”，不能说“所有功能和技术都完全独有”。JMAP 本身及其 queryChanges 数组变换规则来自公开标准，也不能当作自行发明的协议或算法。

## 标准已有语义与项目工程实现

RFC 8620 已分别定义对象 `/get`、`/changes` 的 state 与查询 `/query`、`/queryChanges` 的 queryState，并规定 queryChanges 的 removed/added、索引顺序及数组变换。参见 [RFC 8620 §5.2](https://www.rfc-editor.org/rfc/rfc8620.html#section-5.2)、[§5.5](https://www.rfc-editor.org/rfc/rfc8620.html#section-5.5)、[§5.6](https://www.rfc-editor.org/rfc/rfc8620.html#section-5.6)。本次也读取了工作区保存的 RFC 正文 `work/scope-review/rfc8620.txt` 对应章节。

因此，“双 state 类型”“按 ID 删除后按服务端 index 插入”不能仅因 Mooncakes 中未检出 JMAP 实现便升级为新发明。项目的工程价值在固定支持范围内协调这些语义、约束错误提交，并提供便于解释的输出与证据。

## 当前能力和证书必须写清的边界

当前支持的是两种固定邮箱列表、receivedAt 降序、`collapseThreads=false`、位置 0 的有限前缀和四类只读 Email 方法。它不是完整 JMAP SDK、邮件客户端或邮件服务器；HTTP/TLS/OAuth、Session、SSE、SMTP/IMAP/POP3、MIME、邮件写入、正文和附件均不属于核心交付。实现边界见 `src/email/email.mbt:1-27`、`src/jmap/api.mbt:8-25` 和 `docs/support-matrix.md`。

`Ready` 的含义也限定在内核已接纳响应形成的自洽有界前缀，不承诺多请求读取到了服务端的全局原子快照，更不承诺服务器随后不再变化。两条 state 链的协调不能改写成数据库串行化或分布式全局一致性证明。

证书也有以下实际限制：

1. **内部一致性校验。** QueryKey 和请求形状使用固定 FNV 风格摘要，见 `src/sync/certificate.mbt:744-758`。没有数字签名、可信服务端证明或定理证明系统；它不能证明服务器诚实、响应真实、全量 RFC 正确或业务因果关系。
2. **对象完整性承诺。** 生成阶段读取实际 EmailRecord 并检查投影完整性（`:727-740`），但证书只携带 `objects_complete : Bool`；离线 verifier 对此只检查 Ready 时标志为 true（`:584-585`），没有对象负载可供逐字段重新检查。应说“检查完整性承诺与其他内部约束”，不能说“只凭证书独立重验所有邮件对象属性”。
3. **请求绑定可选。** `plan_binding=None` 在 `:591-594` 直接通过这一层；只有使用带 plan 的构造入口才携带对应绑定。不能宣称每张证书都绑定实际网络请求；FNV 自洽绑定也不是防伪认证。
4. **部分重排的证书生成仍有限制，已复现。** `[a,b,c] → [b,a,c]` 中 c 保持原位，生成器在集合差不足以重放时全删全加（`:813-828`），而 verifier 拒绝原位 remove/add 重叠（`:893-901`）。实际构造返回 `generated certificate is not verifiable: remove/add overlap does not describe a move`。这限定证书生成器的覆盖范围，不能推导同步内核无法应用同一服务端 queryChanges。

本次在复制项目上增加两个最小边界测试，以 wasm-gc 运行，**2/2 通过表示上述限制被成功复现**，不是修复后通过。另一个测试确认：诚实 Ready 构造器会拒绝不完整对象；但在覆盖闭合、两种 token 存在、其他字段自洽、无 plan_binding 的例子中，手动把合法 Pending 证书改为 Ready 并把 objects_complete 改为 true，离线 verifier 会接受。这是证据不携带对象负载的信任边界，不是签名或远端认证绕过。
